# ADR-0070: robots.txt declares content signals, and all three say yes

Status: Proposed

Date: 2026-11-18

## Context

`robots.txt` says which paths a crawler may fetch (ADR-0058: everything, unless the build is a
preview). It says nothing about what the content may be used for once fetched. Content Signals,
a convention with an IETF draft behind it, adds that: one `Content-Signal` line in a crawler's
group, with a yes or no for each of three uses. `search` is a search index and results that link
back. `ai-input` is a model reading the page to answer a question, as in retrieval or grounding.
`ai-train` is training or fine-tuning a model.

A site that declares nothing leaves each operator to guess, and a scan for agent readiness
reports the missing declaration. The site has to pick three values, and the choice is a public
statement of policy, so it is recorded here.

The site is the documentation of an open-source project, under a permissive license, for a
database whose first reader is often an agent (ADR-0005). It already publishes itself for
machines: markdown twins, `llms.txt`, the skill, the docs as a graph. The answers an assistant
gives about relate are better when the model has read these pages, whether at question time or
in training.

## Decision

The indexable build's `robots.txt` declares all three signals as yes, in the group that applies
to every crawler, under a short comment that says what each one means. The values live in one
place beside the function that writes the file, and a test holds the line to them.

A preview build is unchanged: it disallows every path and declares no signal, because nothing on
a preview is meant to be fetched at all.

The declaration is in `robots.txt` only.

## Alternatives considered

- **`ai-train=no`, the example most guides give.** A cautious default, and easy to relax later.
  Rejected: it would ask model builders to leave out the one body of text that teaches a model
  to use relate correctly, which works against the reason the site publishes agent files at all.
  The maintainers may still prefer it; it is a one-word change.
- **Declare only `search` and `ai-input`.** Says what is certain and stays silent on training.
  Rejected: silence on a signal is read as no preference, which is what the site had before, and
  the scan asks for all three.
- **Set it in the host's dashboard.** The host can write a managed `robots.txt` with signals.
  Rejected: the file is generated by the build and follows the indexing switch; a second writer
  outside the repository would not, and the preview and the interim host would differ.
- **Add the convention's legal preamble.** The reference text frames the signals as a reservation
  of rights. Rejected: with nothing reserved there is nothing for it to say, and legal wording
  is not something to copy into a file without review.
- **A response header as well.** A related draft carries the same preferences per response.
  Rejected for now: it is a second place to keep in step, and no consumer of it is known here.

## Consequences

- Crawlers and scanners that read Content Signals find an explicit yes for search, AI input and
  AI training on every path.
- The signals are a stated preference, not access control. A crawler that ignores them is
  unaffected, and the allow rule is what it was.
- Changing a value is an edit to one constant and its test, and a new record if the policy
  itself changes.
- A parser that does not know the line ignores it, as the robots exclusion standard requires of
  unknown lines; the comment lines are comments to every parser.
